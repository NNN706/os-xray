# Полный JSON и подписки

## Настройка профиля

Откройте VPN → Xray, добавьте или отредактируйте профиль. Кнопка Start в строке выбирает профиль и переключает на него единственный активный туннель. Общие Apply/Reconnect применяют активный профиль, а при его отсутствии — единственный включённый. В поле Full Xray Configuration находится весь JSON. Начальная высота редактора — 420 px; нижний правый угол изменяет высоту. Поиск открывается Ctrl/Cmd+F. Кнопка Format JSON меняет оформление, Validate проверяет текущий текст и итоговую конфигурацию установленным ядром.

Импорт принимает вставленный JSON, JSON-файл, HTTPS URL или VLESS-ссылку. Массив из одной конфигурации выбирается автоматически. Для нескольких конфигураций выберите нужную по remarks; они не объединяются. Name заполняется из `remarks` или `Remarks`, при отсутствии значения сохраняется прежнее имя.

Полный импорт сохраняет все разделы и порядок массивов. Дополнительные outbounds и bypass-правила не добавляются. VLESS-импорт создаёт SOCKS 127.0.0.1:10808 и HTTP 127.0.0.1:10809; результат доступен для редактирования. Устаревшие h2/http-ссылки отклоняются; полный JSON можно подготовить для установленной версии ядра самостоятельно.

Для tun2socks нужен loopback SOCKS inbound с no-auth. Приоритет имеет тег `socks`, затем единственный подходящий inbound. При неоднозначности выберите SOCKS inbound явно. Выбор привязан к тегу, а для inbound без тега — к адресу и порту, поэтому перестановка массива не выбирает другой сервер. Отсутствующий SOCKS автоматически не создаётся. Для других адресов 127.x предварительно настройте адрес на lo0; проверка ресурсов отклонит недоступный адрес до остановки туннеля.

HTTP inbound, порты, sniffing, Routing, balancers и observatory остаются частью вашего JSON. В том числе допустим `leastLoad` с `expected: 2`, если это принимает установленное ядро. Ограничение относится к числу активных туннелей, а не к числу outbounds.

## DNS

«Использовать DNS из конфигурации» включено по умолчанию. При выключении блок `dns` остаётся в исходном JSON, становится бледнее и остаётся редактируемым. Только рабочая копия исключает `dns`. Validate проверяет именно её. Системный DNS, Routing и observatory переключатель не меняет. [Назначение DNS Xray](https://xtls.github.io/en/config/dns.html).

## Подписка

Все запросы выполняются сервером с точным `User-Agent: OPNSense`, проверкой TLS и общим лимитом 2000 мс, включая перенаправления и тело ответа. Разрешены только HTTPS URL и HTTPS-перенаправления. URL со встроенными username/password не принимаются; обычный токен в пути или query допускается и не передаётся в аргументах процессов или configd.

Auto Update Subscription по умолчанию Off. При On выберите:

- From Subscription — положительный целочисленный HTTP-заголовок `profile-update-interval` в часах;
- Manual — от 1 до 24 часов.

Если заголовок отсутствует или невалиден, From Subscription не запускает обновления по расписанию; интерфейс показывает причину. Cron проверяет срок каждую минуту. Отсчёт идёт от последнего успешного получения. Для одного профиля действует отдельная блокировка загрузки. При нескольких конфигурациях последующие обновления выбирают единственное совпадение по remarks; при исчезнувшем или неоднозначном имени сохраняется предыдущая версия. [Заголовки Happ](https://www.happ.su/main/dev-docs/app-management#standartnye-parametry).

Успешное обновление заменяет подготовленный JSON, в том числе ручные правки. Если диалог открыт, он получает обновлённый текст при следующем опросе. При ручных изменениях и Auto Update On появляется предупреждение. Изменение отступов и порядка ключей объекта не считается ручным изменением; порядок массивов учитывается. DNS, TUN и настройки расписания хранятся отдельно.

Ошибка HTTP/TLS/сети, невалидный JSON, неподходящий SOCKS или отказ проверки ядром сохраняют предыдущий подготовленный JSON. Активный JSON и PID не меняются при любом результате загрузки. Нажмите Save для изменений в диалоге, затем Apply или Reconnect для применения. Watchdog и загрузочный запуск используют применённый снимок, а не подписку.

## Test

Test работает через SOCKS **применённой** конфигурации с удалённым разрешением имени. `ping-type: proxy-head` выбирает HEAD, `proxy` — GET. Другие режимы используют HEAD; ICMP/TCP-тесты не реализованы. Цель берётся из `check-url-via-proxy`, по умолчанию `https://1.1.1.1`. Поддерживаются HTTP- и HTTPS-цели; для HTTPS проверяется сертификат.

Общий сетевой лимит — 1000 мс. Пример: `OK (200) — connection works — HTTP latency: 148 ms`. Это время до первого байта HTTP, включая SOCKS/TLS, а не ICMP RTT. При таймауте `latency_ms` равен null. Backend сохраняет `result`, `http_code`, `message` и добавляет `latency_ms`, `timed_out`.

## Переход и восстановление

Сначала сохраните резервную копию конфигурации OPNsense и старого пакета плагина. Установщик требует существующие Xray-core, tun2socks и curl. Он не загружает ядро автоматически. Полный JSON с современными параметрами должен приниматься установленным ядром; отказ проверки не следует обходить.

Миграция преобразует старый outbound и bypass в полный JSON с прежним маршрутом direct. Исходные поля не удаляются. Для старого single-instance сохраняется и исходный XML-узел. Конвертации проверяются ядром до сохранения. Неподходящий старый SOCKS или некорректный outbound требуют исправления источника; установщик завершится с ошибкой без удаления старых данных. При единственной подходящей паре старых runtime-файлов сохраняется их применённый снимок для последующей загрузки.

Перед запуском новый JSON проверяется, затем проверяются адреса/порты и TUN. Файлы заменяются атомарно под общей блокировкой Start/Stop/Apply. После запуска проверяются оба процесса, SOCKS и наличие TUN. При ошибке восстанавливается прежняя рабочая конфигурация; незавершённый переход хранит журнал для восстановления следующей операцией. Если сами зависимости или операционная система не позволяют запустить прежнюю версию, файлы и журнал сохраняются, а операция возвращает ошибку.

Несколько старых одновременно работающих туннелей нужно остановить, затем выбрать один профиль. Удаление работающего профиля запрещено; сначала Stop. Интерфейсы OPNsense, шлюзы и правила firewall остаются ответственностью администратора.

Подготовленные и применённые снимки находятся в `/usr/local/etc/xray-core/profiles`, активный снимок — в `/usr/local/etc/xray-core/active.json`. Права файлов — 0600, каталога профилей — 0700. Временные тела API находятся в приватном каталоге `www`; root получает только случайный идентификатор запроса. Вывод ядра при валидации не публикуется, так как он может содержать секреты.

Автоматическое восстановление не является обещанием успешного запуска при повреждённой ОС или отсутствующих бинарниках. Перед использованием требуется проверка на целевой FreeBSD/OPNsense по инструкции TESTING.md.
