# Heartbeat и ограниченный WAN bypass

Один активный Xray и TUN. Проверка через выбранный в полном JSON loopback SOCKS (например, 10808), HEAD `https://cp.cloudflare.com/generate_204`, успешен только HTTP 204. DNS разрешается через SOCKS. Адрес проверки должен маршрутизироваться вашим JSON через proxy. При балансировщике достаточно успешного выбранного пути. Проверка не перебирает outbounds и не создаёт служебных inbounds.

Heartbeat по умолчанию выключен. Интервалы: 15, 30, 60, 120, 300 секунд. Один сбой включает bypass, три последовательных успеха возвращают proxy. Предел запроса — 2000 мс; фактическое обнаружение отказа также зависит от интервала и доступности lifecycle-блокировки. Планировщик раз в минуту запускает защищённый от дублирования короткоживущий worker; это не real-time гарантия. В интерфейсе показаны состояние Xray/tun2socks/TUN, время проверки, HTTP/TTFB, история и устаревшие данные. Manual Test сохраняет отдельный предел 1000 мс и HEAD/GET из метаданных подписки.

## Подключение политики

Автоматический bypass требует явно выбранных правил OPNsense. Сам плагин не создаёт gateways, не отключает их мониторинг, не меняет force_down, системный default, DNS, Unbound или общий rc.conf. BIRD/DNSTAP не устанавливаются.

1. Администратор создаёт существующие TUN и WAN gateways соответствующих семейств.
2. Выделяет отдельные входящие pass-правила на клиентском LAN/VLAN с описанием, начинающимся с `[os-xray]`. Они должны явно задавать IPv4 либо IPv6, не быть floating и уже использовать выбранный TUN либо WAN gateway. Оставьте management и служебные сети вне этих правил.
3. В профиле выбирает Off, All traffic selected by enrolled rules либо Only destination ASN / CIDR, идентификаторы выделенных правил и существующие шлюзы. Для classic rules поддерживается `tracker:12345`, для правил с UUID — UUID. Доступные идентификаторы показывает диалог. Неподходящие и неоднозначные правила отклоняются.
4. В режиме сетей назначения ограничиваются собственным network alias `XRAY_…`. ASN разворачиваются через [официальный API RIPEstat](https://stat.ripe.net/docs/data-api/api-endpoints/announced-prefixes) в префиксы, видимые на последней опубликованной временной отметке. Это наблюдение BGP, а не гарантия владения или полного охвата. Снимок обновляется при Apply/переподключении, не при каждом heartbeat. Ошибка загрузки не заменяет работающий набор. Для воспроизводимости можно использовать явные CIDR.
5. Включает heartbeat и отдельно разрешает WAN bypass. Применяет профиль. До трёх успехов действует bypass.

В обоих режимах изменяются только gateway и destination явно подключённых правил и собственный alias; источники, порядок правил и чужие правила сохраняются. Переход защищён lifecycle/config-блокировками, журналом и откатом при отказе перезагрузки firewall. Состояния соединений удаляются только по labels подключённых правил, чтобы новые соединения использовали нужный путь. Существующие соединения могут оборваться. Global flush запрещён.

В bypass тот же выбранный трафик идёт в WAN, минуя JSON Routing, включая его blackhole/BLOCK. Запреты, которые должны действовать всегда, задавайте отдельными правилами firewall выше правил плагина. При ручном Stop bypass остаётся, автоматический запуск запрещён stopped-флагом; после ручного Start нужны три успеха. Отключение управления политикой оставляет ранее подключённые правила в WAN; администратор может затем восстановить собственную политику.

Ошибки переключения отображаются как unknown/review required: нельзя выдавать желаемое состояние за подтверждённое. Смена default-маршрута не используется для обхода ошибок. Проверка SOCKS доказывает доступность прокси; наличие UP у TUN не заменяет проверку прохождения пакетов тестового LAN-клиента.

## Системный стенд

Рекомендуется Debian runner и отдельная OPNsense VM с консолью/снимком, тестовым LAN-клиентом и доступным WAN. Не используйте рабочий роутер. GitHub Actions runner ставится на Debian; workflow `opnsense-lab.yml` использует labels `self-hosted, linux, opnsense-lab` и environment `opnsense-lab`.

Пока PR остаётся draft и workflow отсутствует в default-ветке, GitHub не покажет ручной запуск этого нового workflow. До включения workflow в default-ветку запускайте скрипты стенда напрямую; это позволяет проверить изменения до merge.

В environment задайте `LAB_SSH_KEY`, `LAB_SSH_TARGET` (`user@host`), `LAB_KNOWN_HOSTS` с заранее проверенным ключом VM. Не присылайте ключи в чат. SSH-учётная запись должна иметь возможность выполнить PHP с правами root только на тестовой VM. Workflow запускается вручную и выполняет только read-only preflight; установка плагина остаётся ручной.

После ручной установки, настройки и Apply запускайте на VM:

```sh
/usr/local/bin/php tests/system/preflight.php
XRAY_ISOLATED_LAB=YES /usr/local/bin/php tests/system/failover.php
```

Для этого скопируйте каталог `tests/system` из проверяемой версии на VM. Второй тест делает Stop/Start активного профиля, наблюдает bypass/восстановление, проверяет сохранность остальных XML-настроек, rc.conf и unbound.conf, пытается восстановить запуск даже при ошибке. Он не блокирует удалённый VLESS-сервер и не доказывает прохождение клиентского трафика.

Обязательно дополнительно проверить с LAN-клиента: доступ в proxy; недоступность VLESS при работающем SOCKS → WAN не позднее интервала + 2 секунды с допуском планировщика; возврат после трёх успехов; чужие назначения/источники не меняют путь; IPv4/IPv6; BLOCK firewall сохраняется; ошибка firewall reload; параллельные Apply/Stop/heartbeat; перезагрузка; смена WAN-адреса. Сетевой отказ моделируйте на внешней тестовой VM/VLESS-сервере, не меняя общие gateways роутера.

Целевая OPNsense/FreeBSD проверка пока не выполнена. Локальные адаптеры и тесты не заменяют её.
